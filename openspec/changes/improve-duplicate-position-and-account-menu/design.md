## Context

持仓表已经用 `(user_id, exchange, symbol, asset_type)` 唯一约束保证同一用户同一证券只有一行，但创建接口没有在业务层识别重复，约束异常最终表现为 500。现有更新接口可以覆盖数量与成本，却无法表达“本次追加买入”以及加权成本语义。账户相关接口已经具备修改密码、退出当前设备、退出全部设备和注销账号能力，本次主要调整信息架构和交互，不改变认证模型。

## Goals / Non-Goals

**Goals:**

- 重复创建稳定返回 HTTP 409 和机器可识别的冲突结构。
- 用户明确确认后，在用户隔离和数据库事务内累加数量并计算加权平均成本。
- 避免并发追加导致丢失更新，保留审计记录。
- 新增桌面与手机都可达的“我的”页面，收纳四项账户操作。

**Non-Goals:**

- 不引入买卖成交流水、手续费、已实现收益或分批建仓历史。
- 不支持负数“累加”模拟卖出；减仓仍留给编辑持仓或后续交易流水功能。
- 不修改密码、令牌吊销和注销账号的既有后端安全规则。
- 不执行数据库结构迁移。

## Decisions

### 1. 创建冲突返回结构化 409

创建接口先锁定当前用户行，再按用户与规范证券键查询已有持仓；存在时抛出业务冲突并返回 `409 Conflict`，响应包含固定错误码 `POSITION_ALREADY_EXISTS` 和已有持仓 ID，不返回其他用户数据。同一用户的创建事务因此被数据库串行化，查询与插入之间不会再发生同用户唯一约束竞争；数据库唯一约束继续承担最终数据完整性保护。相比在约束异常后继续使用已标记回滚的事务查询，用户行锁方案的响应更稳定；相比让前端从中文错误文本判断，结构化冲突也更可扩展。

### 2. 使用独立累加端点，不让客户端先读后写总量

新增 `POST /api/v1/portfolio/items/{id}/accumulate`，请求只传本次追加数量与本次单位成本。服务端按当前用户和 ID 取得写锁，在事务内计算并保存；客户端不提交计算后的总数量，避免并发覆盖。数量必须大于 0，成本必须大于 0。

加权平均成本为：

`(原数量 × 原成本 + 追加数量 × 追加成本) ÷ (原数量 + 追加数量)`

结果按数据库成本精度舍入；原数量为 0 时直接采用本次成本。累加保留原建仓日期、市场、证券、排序和名称，并写 `PORTFOLIO_UPDATED` 审计。

### 3. 前端只在明确冲突时询问

API 请求层新增携带 HTTP 状态、错误码和响应扩展字段的业务错误类型。添加弹窗只有在错误码为 `POSITION_ALREADY_EXISTS` 时展示确认对话；确认后调用累加端点，取消则保持弹窗和原输入，不发起写请求。网络超时仍沿用“先核对列表”的保护提示，不能自动累加或重试写入。

### 4. “我的”作为一级页面

侧边栏新增“我的”，移动端底部导航用“我的”替换“更多”。页面按普通操作与危险操作分区：修改密码为普通操作；退出当前设备、退出全部设备为会话操作；注销账号单独置于危险区域。复用既有确认、密码弹窗和会话清理逻辑，避免再实现一套认证状态管理。管理员“用户管理”继续作为独立入口。

## Risks / Trade-offs

- [加权成本不是完整交易历史] → 明确一期只维护聚合持仓，后续交易流水上线后再迁移。
- [并发创建相同持仓] → 所有创建先锁定当前用户行，使同用户创建串行执行；数据库唯一约束保留为最终完整性保护。
- [并发累加丢失更新] → 仓储查询使用悲观写锁并在单一事务中计算。
- [注销操作误触] → 在“我的”中独立危险区域，继续要求当前密码和二次确认。
- [移动底部入口数量受限] → “我的”替换原“更多”，管理员用户管理在“我的”内提供跳转，同时桌面侧边栏仍有独立入口。

## Migration Plan

1. 先部署兼容旧客户端的后端 409 与累加端点；旧客户端只会显示明确错误，不会再看到 500。
2. 再部署 Web/桌面前端，启用确认累加和“我的”页面。
3. 验证同用户重复、不同用户同证券、并发累加、退出全部设备和注销确认。
4. 回滚前端不会影响后端；回滚后端前应先回滚前端，避免累加端点不存在。

## Open Questions

无；一期采用数量累加和加权平均成本，保留原建仓日期。
