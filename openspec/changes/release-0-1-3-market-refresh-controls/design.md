## Context

0.1.2 的桌面端在持仓接口省略 `quote` 字段时仍把该值加入行情列表，异步响应返回后读取其属性并触发未捕获异常，安装版因此出现登录后闪现首页再黑屏。行情侧目前虽已按新浪、东方财富分别使用 Redis Hash，但调度器只刷新管理员配置的一个来源，且使用全局刷新锁；普通用户的来源选择与管理员全局配置耦合。单股模式则由客户端请求触发上游查询，但主界面固定每 2 秒轮询，无法表达或控制真实请求节奏。

本变更横跨 Spring API、Redis 调度、React/Tauri 桌面端和发布版本，必须同时保证多用户权限边界、缓存隔离、安装版容错以及透明小窗与主页的一致性。

## Goals / Non-Goals

**Goals:**

- 对缺失行情做空值安全处理，并用应用级错误边界提供可见恢复入口。
- 交易时段按管理员配置的同一频率，并行、相互隔离地刷新新浪和东方财富全市场快照。
- 让普通用户在自己的桌面客户端选择读取新浪或东方财富缓存，不影响其他用户。
- 让普通用户在自己的桌面客户端选择全市场或单股模式，不影响其他用户和服务端刷新任务。
- 让普通用户在自己的桌面客户端选择东方财富或雪球单股上游，每次请求按所选来源查询且不改变全局默认值。
- 让单股模式的客户端轮询频率支持 2、5、10、20 秒并在主页和透明小窗一致生效。
- 在首页准确区分服务端快照刷新频率与客户端查询频率。
- 完成 0.1.3 的本地服务、安装应用和发布验证。

**Non-Goals:**

- 不引入交易日历、WebSocket 推送或新的第三方行情源。
- 不让普通用户修改服务端刷新频率、服务端默认模式或服务端默认来源。
- 不把客户端偏好同步到用户账号或 PostgreSQL；一期按设备保存。
- 不改变非交易时段保留最后一次成功快照、Redis 数据不主动过期的既有规则。

## Decisions

### 1. 工作模式与来源是本机偏好，服务端配置仅保留默认值

客户端使用持久化本地偏好保存 `MARKET_SNAPSHOT | SINGLE_STOCK` 模式、`SINA | EASTMONEY` 快照源和 `EASTMONEY | XUEQIU` 单股源，普通用户均可修改。持仓、行情与状态请求携带可选的 `mode` 及对应来源；服务端对枚举严格校验，并按请求模式读取 Redis 或触发单股查询。未传值时回退管理员配置的默认模式和默认来源，以兼容旧客户端。

选择本地偏好而不是修改全局 `market_data_config`，可避免一个普通用户切换来源影响所有在线用户。账号跨设备同步留待个性化设置阶段。

### 2. 两个来源持续并行刷新且状态完全隔离

调度器不再依赖服务端默认工作模式，在交易时段到期后始终同时提交新浪、东方财富两个刷新任务并等待本轮完成。每个来源拥有独立的刷新锁、最近尝试时间、成功时间和健康状态；一个来源超时或失败不会取消另一个来源，也不会删除其最后成功快照。管理员配置的 `refreshSeconds` 同时作用于两个来源，并且只有管理员接口可修改该值。

选择服务端并行而非客户端各自触发全市场抓取，可复用一次抓取服务所有用户，避免对 AKShare 上游造成用户数倍增的压力。并行任务使用受控执行器，防止定时器无限创建线程。

### 3. Redis 快照继续按来源永久保存

沿用 `trading:quotes:akshare:snapshot:sina` 与 `...:eastmoney` 两个 Hash，刷新时仅以新快照原子替换或更新对应来源；不设置 TTL。刷新锁改为来源后缀键，元数据也按来源维护。非交易时段不发起刷新，接口继续返回最后一次成功数据。

该方案无需数据迁移，并与 0.1.2 已存在的缓存兼容。

### 4. 请求级模式与来源显式传递，不使用全局可变上下文

为行情提供器增加不可变的请求选项，由 Controller 经 Registry 传到 AKShare provider。持仓列表接口和必要的行情、状态接口接受可选 `mode` 与来源查询参数。其他 provider 可以忽略该选项。

不使用 ThreadLocal 或临时修改全局配置，因为异步执行和并发用户会导致来源串扰，且难以测试。

### 5. 单股来源和查询频率由客户端请求驱动

桌面端同时保存本机工作模式、`EASTMONEY | XUEQIU` 单股来源和 `2 | 5 | 10 | 20` 秒频率。模式或来源偏好缺失时使用服务端配置中的对应默认值，频率缺失或非法时回退 10 秒。React Query 在单股模式下用该频率设置主页和透明小窗的 `refetchInterval`；查询键包含模式、快照来源和单股来源，切换后立即重新请求。全市场模式仍可用较短客户端读取周期访问 Redis，但首页只展示管理员配置的服务端刷新频率，避免把两种频率混为一谈。

客户端在持仓和行情请求中携带受枚举校验的可选 `singleSource`。服务端仅在单股模式使用该请求值；未传时回退管理员配置的默认单股源。在东方财富模式下继续过滤不受支持的北交所标的，雪球模式保持现有交易所能力。普通用户的选择不写 PostgreSQL、不修改 `market_data_config`，因此并发用户可分别使用不同来源。

单股模式继续按请求触发 AKShare 单股接口，并复用网关现有的分来源短时缓存与并发合并能力；因此“客户端查询频率”就是该设备产生后端查询的节奏，而不是服务端后台任务。

### 6. 黑屏采用数据边界和渲染边界双重防护

行情数组使用 `quote != null` 的类型保护，同时允许 API DTO 的 `quote` 为缺失值。应用根节点增加 Error Boundary，捕获无法预见的渲染异常并显示错误说明和重新加载按钮。定向测试必须覆盖“部分持仓有 quote、部分省略 quote”的真实 JSON 形态。

仅修正过滤条件无法防止未来其他组件异常导致整页空白；仅加 Error Boundary 又会掩盖当前数据缺陷，因此两层都保留。

### 7. 版本与发布

桌面端 package、Cargo 与 Tauri 配置统一升级为 0.1.3。发布前先在本机 PostgreSQL、Redis、AKShare 和可见 Terminal 服务中验证，再构建 macOS 安装包进行真实登录冒烟；随后部署云端后端并构建 Windows/macOS 安装包发布到 GitHub。两个平台的 SHA-256 清单必须使用跨平台 LF 换行，使 macOS、Linux 和 Windows 用户均可直接验证下载资产。

### 8. 主窗口使用固定可视区与局部滚动

`html`、`body`、`#root` 和主页面容器统一使用窗口高度并禁止页面级纵向溢出。工作台改为可压缩的纵向 flex/grid：页头、状态与汇总区保持可见，自选卡片占据剩余空间，只有卡片内的行情表在标的过多时滚动。行情配置页与管理页同样固定在可视区，长表格使用内部滚动；在较矮窗口中通过紧凑间距和卡片高度自适应，而不是扩张整个文档。

不采用按比例缩小整个 WebView，因为这会降低文字可读性和点击目标尺寸；局部滚动只用于理论上无法一次展示的任意长度数据集，不会产生窗口级上下滚动条。

## Risks / Trade-offs

- [两个全市场来源同时抓取会提高服务端 CPU、网络和上游压力] → 使用固定大小执行器、共享管理员频率和来源独立防重锁，并保留最小频率校验。
- [新浪全市场接口耗时可能超过刷新周期] → 同一来源未完成时不重入，失败或超时只记录健康状态并保留旧数据。
- [本机全市场来源、单股来源和频率偏好不会自动跨设备同步] → 明确作为 0.1.3 设备级设置，后续用户个性化阶段再迁移到账号配置。
- [普通用户选择东方财富时北交所标的无法查询] → 服务端按请求来源过滤不支持的交易所并返回无行情，不回退到另一来源，以确保实际请求与用户选择一致。
- [AKShare 旧版本的雪球接口可能因上游响应格式变化而失效] → 固定升级到经本地真实请求验证的 AKShare 1.18.72；来源调用仍保持故障隔离，不在用户未选择时跨源降级。
- [全市场模式客户端仍会频繁读取 Redis API] → 读取不触发 AKShare，上游负载只由服务端刷新频率决定；后续可增加 ETag 或推送优化。
- [错误边界可能隐藏详细异常] → 前端记录完整错误日志，用户界面仅展示可恢复提示，不输出敏感信息。
- [大量自选或用户记录无法在有限高度内全部逐行展开] → 固定导航与摘要，长数据仅在所属列表卡片内部滚动并保持表头可见。

## Migration Plan

1. 先部署兼容旧客户端的后端：查询参数可选，Redis 继续使用现有来源键。
2. 启用双源刷新，确认两个来源的缓存时间、健康状态及失败隔离。
3. 构建 0.1.3 客户端并验证旧本地存储缺失时默认使用 10 秒、服务端默认模式、默认快照源和默认单股源。
4. 在本地安装版复现账号上验证登录后不黑屏，再更新云端服务并发布安装包。
5. 回滚时可退回 0.1.2 后端；现有 Redis 键和数据库结构未破坏。客户端若需回滚，不读取新增本地偏好即可。

## Open Questions

无阻塞问题。账号级偏好同步、节假日交易日历和 WebSocket 推送作为后续版本候选，不纳入 0.1.3。
