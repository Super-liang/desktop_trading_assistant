## Context

能耗修复代码和 0.1.4 新构建已在工作区完成验证，但 `/Applications` 中仍是同版本号的旧二进制。现场采样显示旧进程持续高 CPU，且相同版本号使安装状态不可辨识。本次只处理版本一致性、本机覆盖安装和修复包验收。

## Goals / Non-Goals

**Goals:**

- 让前端、Tauri 与 Rust 元数据统一显示 0.1.5。
- 构建明确包含既有能耗修复的 macOS 应用。
- 安全退出旧进程并以 0.1.5 覆盖安装，不删除 WebView 用户数据。
- 用二进制指纹、运行路径、UI 操作与进程采样证明实际运行的是新包。

**Non-Goals:**

- 不新增行情、认证或服务端功能。
- 不发布 GitHub Release，不部署服务器，不构建 Windows 安装包。
- 不清理用户登录态、自选、持仓或应用缓存。

## Decisions

1. **统一提升到 0.1.5**：同时修改 npm、Tauri 和 Cargo 版本，避免仅修改界面展示造成包元数据不一致。继续使用 0.1.4 会让用户无法判断安装是否生效。
2. **退出后原位替换应用包**：先正常终止当前进程，再复制新 `.app` 到临时路径并原位替换，避免运行中的 bundle 被部分覆盖。用户数据位于系统 WebView 数据目录，不随 `.app` 替换删除。
3. **以运行二进制为验收对象**：安装后核对 `Info.plist`、可执行文件哈希和进程命令行，再登录并测试导航、小窗与 CPU，而非仅依据构建命令成功。
4. **保留可回滚副本**：覆盖前将旧应用重命名为带时间戳的备份；若新包无法启动，可退出新进程后恢复备份。

## Risks / Trade-offs

- [同一 Bundle ID 导致 macOS 复用旧进程] → 覆盖前确认旧 PID 已退出，安装后再启动。
- [直接覆盖时产生不完整应用包] → 先复制到 `/Applications` 下的临时目录，完成后再重命名切换。
- [本机未签名构建触发 Gatekeeper] → 保持现有本地构建签名策略，仅用于当前开发机验证，不作为公开发布包。
- [现场 CPU 降低但长期问题仍可能复现] → 记录启动后和持续运行后的多次采样，并保留旧包备份便于对比。

## Migration Plan

1. 更新版本元数据并运行前端、Rust 测试与生产构建。
2. 退出当前 `/Applications` 旧进程并确认关联进程结束。
3. 备份旧 `.app`，复制并切换 0.1.5。
4. 启动 0.1.5，验证版本、登录、导航、透明小窗和 CPU。
5. 若启动或功能失败，退出新进程并恢复旧应用备份。
